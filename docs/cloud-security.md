# Cloud security controls

The cloud stack forces paper mode and disables server real-market paper decisions and legacy ingestion. The runtime loader accepts only the API token, database app password and four secure RPC URLs. It refuses unknown fields (including signer/seed/private-key fields), malformed credentials and insecure transports. It loads file secrets into process memory at runtime, never into Compose interpolation. No wallet signer, funded credential or transaction broadcast path is added.

`private/` is mode 0700, credential files mode 0600. The new cloud runtime file is owned by UID 1000; database password files by UID 70. Root runs host maintenance. `.env`, `.env.*` (except the template), `private/`, backup archives, PEM/key files and build outputs are excluded from Docker context and Git ignore rules. Documentation is excluded from the image context as well. The existing `.env` and `.env.save` were restricted to 0600 without changing their contents. Ignore rules cannot prove an absent Git history is clean; verify `git ls-files` in the real checkout and remediate any already tracked secrets separately.

Never publish `docker compose config`, `docker inspect` environments, shell tracing, runtime JSON, RPC URLs, private attribution or raw provider errors. Use `manage.py validate` and `docker compose ... config -q`. Public cloud Compose configuration uses file paths only; database and API credentials are absent from its resolved output. Cloud request errors use a fixed message and automatic per-request URL logging is disabled, preventing upstream errors or rejected user values from entering logs. Host scripts suppress subprocess failure details; systemd logs carry fixed failure messages and numeric/enum monitoring summaries. Docker/host root can still read all secrets; disk encryption, least-privilege administration and protected off-host storage remain operator responsibilities.

The app and research containers run as UID 1000 with read-only roots, dropped capabilities, no-new-privileges, bounded temporary storage, process/memory/CPU limits and bounded Docker logs. PostgreSQL runs as its nonroot UID 70 with a persistent writable data mount. Caddy runs as UID 1000 on unprivileged internal 8080/8443, mapped to public TCP 80/443. Its persistent certificate volumes are initialized for UID 1000. No service uses privileged mode, host networking, the Docker socket or public database ports. The internal database network cannot route to the Internet; only the app shares that network. Research has no database credentials in Compose; its runtime credential file necessarily contains the app database password, but the research code does not use it and its network cannot reach PostgreSQL.

The PostgreSQL bootstrap owner is separate from the app role. Fresh initialization grants `mintbot` only connection/schema usage and SELECT/INSERT on the event audit table. It cannot create schema, modify wallets/orders/positions, or become a superuser. Existing cloud databases are never migrated or re-granted automatically; inspect role/schema compatibility during updates.

Caddy automates TLS renewal and redirects HTTP to public HTTPS 443 explicitly. Request bodies are capped at 32 KiB, headers at 16 KiB, with bounded downstream/upstream timeouts. Security headers include HSTS, frame denial, content sniffing denial and no referrer. The app supplies its existing CSP and checks bearer tokens and same-host origins for all `/api/` routes, including the new readiness route. Reverse proxy headers preserve existing authentication. No access log containing tokens or RPC query strings is enabled. A valid TLS certificate is still an external deployment prerequisite.

Manual rotation must be deliberate and coordinated:

- API token: stop app access, securely edit the runtime file, recreate only the app, verify 401 for old token and authorized access for the new token; update operator clients. Do not place either value in command arguments or reports.
- Application database password: take a verified encrypted backup, stop the app, change the `mintbot` role password through a protected interactive PostgreSQL session, update runtime JSON and `database-app-password` together, restore ownership/modes, recreate app and verify readiness. The init password file alone never changes an existing database role.
- Bootstrap password: change the owner role password interactively and update `postgres-password`. Preserve the previous version only in an approved secret vault. Do not reset a volume to change credentials.
- RPC credentials: stop bounded research through its existing sticky stop procedure, obtain/review new provider credentials, update secure endpoint fields and the matching attribution mapping together, validate and run only a finite diagnostic. Credential rotation never grants provider independence or coverage approval.
- Backup recipient: generate a replacement offline key/certificate, install only the public certificate, run a backup and isolated restore with the replacement key. Retain old decryption keys for the full retention period.

No secrets were automatically rotated in this phase. Existing safety evidence, protocol/deployment pins, coverage epochs, stop fences and quarantines remain authoritative.
