Those errors suggest version 1 but supply no successful transaction, raw bytes, accounts, logs or metadata. They do not prove transaction success, finality or selected-service compatibility.

The package manifest's ^1.98.4 range actually locks **@solana/web3.js 1.99.0**. Its installed VersionedMessage dispatch includes MessageV1. Maintained decoding support exists; a blanket claim that Solana SDKs cannot decode v1 would be incorrect. The application's SDK inspector still requests v0. Native VerifiedReadRpc and HttpRecoveryRpc previously requested v1, and creations() admitted v1, despite the narrower inspector. ParsedChainTransaction lacks v1 transactionConfig validation and raw-byte/account-index equivalence checks. Treating successful JSON parsing as full compatibility was unproven.

No runtime source change is retained. An attempted blanket version restriction broke existing historical/provisional fixture contracts and was reverted rather than changing original tests. The existing SDK inspector retains its version-unsupported RPC failure at max 0; native parsed readers still request max 1 and the read-only creation decoder still extracts historical v1 metadata. This distinction is explicitly audited, not described as complete v1 encoding/economic support. Two new offline controls verify inspector refusal without retries/escalation and rejection of unknown creation versions. No reader, dependency, whitelist or authorization was added.

Solana's [migration guidance](https://solana.com/upgrades/larger-transaction-sizes) identifies v1 message resource configuration, a total priority fee in lamports, removed address lookups, and operator storage requirements. Its [RPC structures](https://solana.com/docs/rpc/json-structures) define transaction metadata and account representations. These sources were consulted on November 15, 2026; they describe the protocol, not evidence from the absent operator services.

Required next proof: successful finalized signed base64 and JSON fixtures from the selected independent services, cryptographic identity and original creation attribution, validated config/fee units, strict top-level/inner instruction indices and invocation stack, complete metadata, and account reconstruction matched to the maintained SDK. Test malformed config, unknown versions, bounds, missing metadata, loaded-address inconsistencies, signature/slot conflicts and legacy/v0 regressions.
